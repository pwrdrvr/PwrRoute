1Settings › Privacy

A link is private data, and the router sees every one. This pane says in plain words what is kept, where, and for how long, and it is the only place a URL can be allowed onto disk. Today the router keeps the last 200 dispatches in memory (Options.capacity) and nothing on disk; the pane makes the count editable, adds an age limit, and adds the journal, which is off by default. The disclosure sentence under the journal switch is rendered verbatim by the app, one sentence per level, so the Activity footer, the pane and the docs say the same thing. A new Privacy item joins the Settings nav after Configuration; Diagnostics keeps logs and the data folder.

1aThe default. Retention is a count and an age; the journal is off, so the file row is dimmed and Reveal and Clear now with it. Export is always available: it writes what Activity shows, at each record's level, to a file you choose. The last card explains the three per-rule levels with the rules.json field for each.

2Activity › find the unrouted ones, add a narrow rule

The reason Activity exists: a link opened in the wrong browser and the person never saw its URL, because the browser redirected at once. Rows that were routed can be saved as the rule’s example, so a later rule cannot take them silently.

3Rules › examples, Run tests, Save as test

Every rule can carry examples: URLs that must resolve to it, stored in rules.json next to the rule (rules[].examples, rewrites[].examples with the URL each becomes). Top-level tests pin a whole resolution: a URL, an optional opener, and the browser, profile and URL expected. Run tests resolves all of them against the rules as saved and reports each failure as input, expected, actual and which rule won instead. A failure here is the rule that was just added or moved taking a link that was someone else’s; the strip says so before the person moves on.

3aHandler 2, github.com/* → Firefox, was added a minute ago and pushed the old handler 2 to 3. Run tests ran on save: 12 passed, 1 failed. The failure row names the input, what handler 3’s example expected, what happens now, and the winner. The chips under each rule are its examples; the failed one says where it went.

4An agent does the same, over MCP

The same three steps as turn 2 and 3, for a local agent with the Editor role: read Activity for the unrouted links, test a proposed patch, apply it. pwrroute_rules_test is new: it runs the saved examples and tests against a patch without writing it. pwrroute_rules_apply runs the same tests itself and refuses a patch that fails any, so an agent that skips step 2 still cannot change old routing; the refusal carries the regressions in the same shape. Records come back at their privacy level: a host-only record has host and no url, and records that keep nothing are a count.

4aThree calls. The agent asks for unrouted links, proposes github.com/* at the top, tests it, sees the regression, and the apply it tries anyway is refused with the same failure. The fix is to place the handler below handler 3, or to pass the examples it means to change in update_examples; either way the user’s saved routing cannot be changed silently.

Why apply refuses instead of warning. An agent will take a warning as a note and move on; the user finds out when a link opens in the wrong browser, and the URL that would tell them why has already been redirected away. Refusing with the failure list costs the agent one more call and keeps every saved example true. Changing an example on purpose is a named parameter, so the intent is in the request and in Activity’s agent log (“pwrroute_rules_apply · moved 1 example to handler 2”).

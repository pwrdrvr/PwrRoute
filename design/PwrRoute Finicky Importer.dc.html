1Importer › finding a config

The importer is one window with three steps: Review, Place, Choose source. It reads the config the way the router does, by evaluating it in QuickJS, and inspects the handlers and rewrites the config produced, not its text. It writes only rules.json, and never the file it read. It can be opened from four places; the first time discovery finds a config while visual rules are in charge, the Rules view says so once.

2Importer › review · place

Each rule gets one verdict. Imports: string, wildcard and regex matchers, browser names with profiles, string rewrites and defaultBrowser become visual rules that run through the same Finicky API, so they behave identically by construction. Stays JS: function matchers and url functions, which no visual rule can prove equal. A function that looks like a visual rule gets a suggestion, tested against recent links and clearly not a proof; it is off unless ticked.

3Importer › choose source · result

The last step decides what the router reads afterwards, because the rules that stay JS only keep working while the config is selected. Import writes rules.json in one atomic save (RulesFile::save stages and renames), keeps the previous file for Undo import, and the router hot-reloads. If the config does not load, there is nothing to review, and the importer says why instead of showing an empty list.

3aTwo outcomes, and the one that drops something says exactly what. With nothing left in JS the step is skipped and visual rules are selected.

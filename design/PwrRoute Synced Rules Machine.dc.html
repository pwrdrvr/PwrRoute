2This machine › destinations and rule sets

Browsers and profiles differ between machines, so rules can open links in a named destination (destinations[] in rules.json: Work 1, Work 2, Personal, PwrDrvr), and rules can belong to a rule set (sets[], rules[].set) that a machine turns off. What a name opens on this machine, and which sets are off here, live in machine.json next to rules.json, which never syncs. The editor shows and writes the synced file; the This machine card writes machine.json. Turn 1, Settings › Sync and its folders, is in PwrRoute Synced Rules.

2aThis machine, with named destinations and rule sets in rules.json. Each destination row: the name, what it opens here (the browser badge and profile, as a lane draws them), and where that comes from: a neutral synced chip, or an accent this Mac chip with the synced value under it and Use synced to go back. A browser this Mac lacks turns its row to the warning tone with the way out on the row. Rule sets list each set with its count and a switch; a set this Mac overrides carries the this Mac chip.

3Sync status in the window and the menu bar

The person should be able to tell that sync works without opening Settings, and should not miss a conflict. The rail foot already says what the router is doing (routing, next link · Microsoft Edge) and is on every main-window screen, so sync gets a line there. The strip holds the rules source chip and warnings like a failed test, so only the two states that need action add a chip there. The tray gets one line.

3aRecommended: the rail foot, one line under routing and above the build block, whenever a folder is set up. It reads like its neighbours (mono, lower case) and is a click to Settings › Sync. Quiet when all is well; the warning and danger tones carry the two states that need the person. Nothing is drawn when sync is off.
